Temporary Email for Developers & QA: Test Signups Without the Mess

Every signup flow needs a victim inbox: registration, email verification, OTP, password reset, notification preferences. Maintaining shared test mailboxes is how teams end up with flaky suites and mystery state. Scripted disposable inboxes give every test run a fresh address, then throw it away. Here's the pattern that works.

The 30-second scripted loop

Hi Temp Mail's relay is a plain 1:1 mirror of the Mail.tm API with CORS enabled, so scripts and CI runners can call it directly — full contract in openapi.json, walkthrough in the developer docs. The loop per test:

BASE=https://hitempmail.app/api/mailtm
ADDR="qa-$GITHUB_RUN_ID-$RANDOM@<domain-from-GET-/domains>"
PASS="$(openssl rand -hex 8)"
curl -s -X POST $BASE/accounts \
  -H 'Content-Type: application/json' \
  -d "{\"address\":\"$ADDR\",\"password\":\"$PASS\"}"
TOKEN=$(curl -s -X POST $BASE/token \
  -H 'Content-Type: application/json' \
  -d "{\"address\":\"$ADDR\",\"password\":\"$PASS\"}" \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["token"])')
# ... drive your signup form with $ADDR ...
# poll until the verification mail lands (timeout ~90s):
for i in $(seq 1 18); do
  N=$(curl -s -H "Authorization: Bearer $TOKEN" \
    "$BASE/messages?page=1" | python3 -c 'import sys,json;print(json.load(sys.stdin)["hydra:totalItems"])')
  [ "$N" -gt 0 ] && break; sleep 5
done

What to assert

Don't just check "an email arrived." Assert the things that actually break in production: the message arrives within your SLA (measure it — delivery latency is the #1 signup killer); the OTP matches the expected format and is single-use; resend generates a new code and invalidates the old; links carry the right token and expire correctly; and unsubscribing or deleting the account stops the mail. Extract codes the same way the app does — first 4–8 digit group near words like "code" or "verify".

CI hygiene

Use a unique address per run (parallel jobs sharing one inbox is the classic flake factory). Delete the mailbox at test end (DELETE /accounts/{id}) so provider quotas don't rot. Back off on HTTP 429 instead of hammering — roughly 30 requests/minute is the upstream neighborhood. And never point these scripts at production user data: disposable inboxes are for test environments, full stop.

Manual QA counts too

Not everything needs a script. For exploratory testing, open the app, copy the address into your staging build, and watch codes land with auto-detected copy chips. Bookmark the mailbox and tomorrow's regression run starts from the same address.

Quick answers

Is there an official API? Yes — the keyless relay at /api/mailtm, specified in openapi.json.

Can CI create unlimited addresses? Within upstream rate limits (~30 req/min). One address per run, delete afterwards.

Why did my test address get rejected? Some apps block disposable domains. That's product behavior worth asserting — and a reason to keep one permanent test inbox alongside.
